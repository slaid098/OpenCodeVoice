# ADR 0010: Config v2, retry policy, and IndexedDB recovery

- **Date**: 2026-10-20
- **Version**: 2.0.0

## Статус

Accepted.

## Контекст

В 1.x настройки лежали набором плоских ключей (`groqApiKey`, `model`, `language`, `whisperPrompt`, `temperature`, `endpoint`, `autoSubmit`), не было ни LLM-секции, ни провайдеров, ни ретраев. Любая ошибка STT означала потерянную запись: аудио жило только в памяти вкладки. С телефона это особенно болезненно — сеть нестабильна, вкладка может быть выгружена Android-ом.

Для 2.0.0 нужны:

- единая версионированная конфигурация с миграцией;
- автоматические повторы для временных ошибок;
- сохранение записи до сетевого запроса и восстановление после reload;
- повтор операции с той стадии, на которой произошёл сбой, без дублирования вставки.

## Решение

**1. Конфиг v2 — одна JSON-строка.** `ocvd.config.v2` в GM storage, `schemaVersion: 2`, секции `stt`, `llm`, `behavior`, `retry`. `loadConfig` при битом JSON возвращает defaults и не падает. `normalizeConfig` чистит типы и зажимает числа в допустимые диапазоны. `validateConfig` возвращает список русских ошибок (URL, ключи, temperature, длительность, попытки) и используется панелью перед сохранением.

**2. Миграция 1.x.** Если `ocvd.config.v2` отсутствует, читаются старые ключи. Провайдер STT определяется по endpoint (`api.groq.com` → `groq`, `api.openai.com` → `openai`, иначе `custom`), ключ/модель/язык/промпт/temperature переносятся в `stt.*`, `autoSubmit` — в `behavior.autoSubmit`. Результат сразу сохраняется в v2; старые ключи не удаляются, но больше не читаются.

**3. Retry-политика.** Общий `withRetry` в `http.ts`:

- повторяются network/timeout, `408`, `425`, `429`, `5xx`;
- не повторяются `400`, `401`, `403`, `404`, `409`, `422`;
- задержка `min(maxDelayMs, baseDelayMs × 2^(attempt−1))` с jitter 0.5–1.0;
- `Retry-After` (секунды или HTTP-date) ограничивается `maxDelayMs`;
- `AbortSignal` отменяет текущий `GM_xmlhttpRequest` и не запускает новый retry;
- defaults: 3 попытки, 800 мс, 8 с.

**4. Запись сохраняется до STT.** После `stop()` аудио конвертируется в `ArrayBuffer` и пишется в IndexedDB (`failures`, keyPath `id`) со стадией `stt`. Дальше запись обновляется по мере прохождения стадий (`rawText`, `cleanText`, `stage`, `attempts`, `error`). При успешной отправке запись удаляется.

**5. Восстановление.** `getLatestFailure()` при загрузке страницы показывает баннер (без автоматической вставки). Действия зависят от стадии:

- `stt` — «Повторить» (аудио уже в IndexedDB);
- `llm` — «Повторить очистку» и «Вставить сырой текст»;
- `insert`/`submit` — «Повторить отправку/вставку»; повторная вставка использует `replaceText`, если `rawInserted = true`, поэтому текст не дублируется;
- «Удалить» и «Настройки» доступны всегда.

**6. Гигиена хранилища.** Не более 5 записей и не старше 7 дней (`pruneFailures`). При `QuotaExceededError` удаляется самая старая запись и операция повторяется. `navigator.storage.persist()` запрашивается один раз; `estimate()` показывается в диагностике. Без IndexedDB остаётся только текст в памяти/GM storage, аудио не сохраняется — пользователь предупреждается.

**7. Pipeline как state machine.** `src/pipeline.ts` не зависит от DOM: recorder, transcribe, cleanup, insert, replace, submit и storage инжектируются. Это позволяет тестировать happy path, ошибки каждой стадии, cancel, retry и восстановление без браузера.

## Последствия

- Пользовательские настройки 1.x мигрируют автоматически; откат на 1.0.7 потребует повторного ввода ключа (старые ключи остаются на месте, но 2.x пишет в новый ключ).
- Аудио занимает место в IndexedDB; лимиты и prune ограничивают рост.
- IndexedDB может быть вычищен браузером; `persist()` снижает вероятность, но не гарантирует. В этом случае запись теряется — это документированное ограничение.
- Автоматический retry не заменяет ручной: после исчерпания попыток пользователь видит баннер и может повторить, не теряя запись.
- Ключи API лежат в GM storage в открытом виде; это ограничение userscript-менеджера, а не решение. Документировано в README.

## Альтернативы

### 1. Плоские ключи GM storage, как в 1.x
- **Плюс**: обратная совместимость без миграции.
- **Минус**: десятки ключей, нет атомарности, сложно версионировать и валидировать. Отвергнуто.

### 2. localStorage вместо IndexedDB
- **Плюс**: проще API.
- **Минус**: не хранит `ArrayBuffer`/Blob без base64, лимит ~5 МБ, синхронный. Отвергнуто.

### 3. Автоматическая повторная вставка после reload
- **Плюс**: меньше действий пользователя.
- **Минус**: опасна: пользователь мог уже вставить/отправить текст вручную, возможны дубли в composer. Выбран баннер с явным действием. Отвергнуто.

### 4. Бесконечный retry
- **Плюс**: максимальные шансы на успех.
- **Минус**: при неверном ключе или недоступном сервере это бессмысленная нагрузка и зависший интерфейс. Ограничено 3 попытками (настраивается 1–5). Отвергнуто.
